# Open work

This document tracks known gaps and planned work in this repository. It is kept here, rather than in an issue tracker, so a reader looking at the code can see in one place what is not done yet, why it matters, and what would make an obvious-looking fix wrong.

## Escape counting correctness

These affect the escape detector's numbers directly, and the first one should land before the others are worth chasing further, since it changes the shape of what the rest measure.

- **ESCAPED and FAILS_ON_MAIN are now one bucket on the page, and the two follow-ups that leaves are below.** The baseline decided which of the two names a conviction got, on a single failure, and that knife-edge sorted severity wrongly — 25 near-deterministic regressions (before-rate under 5%, after-rate at or above 50%) sat in FAILS_ON_MAIN against 1 in ESCAPED, while 323 of 349 ESCAPED rows rested on an after-rate under 5%. The page's ESCAPED category is the union of both stored names (`escapes.MERGED_ESCAPE_VERDICTS`), the baseline is a split under it, and the distinct-test count is printed beside the conviction count. Not an open item; recorded because the next two are what it left behind, and because reverting it is an edit to that one tuple — no verdict, count, schema or `CHECK` constraint was touched.
- **The currency check has never been asked of the already-failing half of the merged bucket.** `assess()` calls `check_currency` only where the verdict it just stored is `ESCAPED` (`escapes.py`, the loop at the end of `assess`), so every FAILS_ON_MAIN row has `recent_runs`/`recent_failed`/`recent_checked_at` null. Those rows are now in the same bucket as the escapes, so the pane's "main now" split reads mostly *not checked yet* and the Current damage column is a dash for them — truthful, since nobody asked, but it means the split is far less informative than the bucket it divides. Extending the check to both verdicts is a write-and-network change (roughly 2,282 more rows at one query per row per day on one local measurement), so it wants its own pass rather than a tweak here.
- **A conviction count in the merged bucket is not a regression count, and nothing deduplicates it.** One landed regression makes a fresh conviction on every later pull request whose build trips the same test: `imported/w3c/web-platform-tests/css/css-cascade/all-prop-initial-xml.html` had 29 convictions from one underlying regression, its `failed_before` climbing 1, 2, 3, 4, 7, 8, 11, 19, 20 as it poisoned each later baseline. The page now prints the distinct-test count beside the conviction count so the two cannot be confused, which is a disclosure rather than a fix — there is still no grouping of a cascade into the one regression behind it, and any figure quoted as "regressions" has to be the distinct-test count or a deduplicated one.

- **The landing-window and currency-window sentences on an escape row are not counted over comparable windows, and the currency window is not clamped to the landing.** `ews_dashboard/analysis/escapes.py`'s `check_currency` (around line 541) fetches runs from `now - CURRENCY_WINDOW_SECONDS` to `now` with no lower bound at the landing time, while the landing-window counts are taken strictly either side of `landed_at`. Because a stored row only reaches `ESCAPED` after a settling delay, the currency window can and does reach back past the landing, so `recent_runs` can exceed `runs_after` and the two sentences on the same row describe overlapping but different spans. The fix is to clamp the currency window's start to `max(candidate.landed_at, now - CURRENCY_WINDOW_SECONDS)`, which by construction restores `recent_runs >= runs_after`. Two riders belong in the same change: the window becomes variable-length, so a stored row needs to keep its own span rather than assuming the config constant; and the results.webkit.org page-size cap below has to be fixed alongside it, or `recent_failed` can still land under `failed_after` even with the window clamped.
- **The results.webkit.org runs endpoint returns at most `RUNS_PER_QUERY = 100` runs per response group** (`ews_dashboard/results.py:64`, passed as the endpoint's `limit` parameter at `:310`), **and that limit applies per configuration group in the response, not per query as a whole.** A window with more OS versions/models than fit under the cap silently drops the oldest runs in each group with nothing in the stored row to say so, so `recent_runs`/`runs_after` are floors that get tighter the wider the window. Needs either a higher limit or pagination of the endpoint.
- **Both count paths pool every OS version and model under one platform/style/flavor "configuration," not the specific queue a row is labelled with** (`ews_dashboard/results.py`, the `_runs_in`/`_fetch_runs` path, documented around line 252 onward). The queue name printed on an escape row is not the actual scope of the runs counted for it — it is every main bot sharing that platform/style/flavor.
- **`RUNS_SETTLING_SECONDS` is applied when reusing a stored verdict (`_stored`, `escapes.py` around line 489) but not by the counting or subcategory queries** (`_counted_verdicts` and `escape_subcategories`, `escapes.py`), so provisional verdicts sit in the same denominator as settled ones. On one local measurement this put the large majority of counted verdicts in the provisional state, with `CONTAINED` the bucket most likely to still flip to `ESCAPED`; treat the exact share as an order of magnitude, since it depends on the ingestion window measured.
- **The "still failing" / "recovered" read of the currency check applies no rate threshold at all**, unlike the landing-window escape grade. `currency_for_counts` (`escapes.py:152`) reads `STILL_FAILING` whenever `recent_failed` is truthy and `RECOVERED` otherwise, so one failure in a few hundred currency runs reads identically to a much higher rate. The 50% threshold that grades the landing window (`ESCAPE_FAILURE_PCT`, `config.py:33`) is never applied to the currency window.
- **The currency partition has a hole that prints as a recovery.** `currency_for_counts(recent_runs=1, recent_failed=None, recent_checked_at=100)` returns `RECOVERED`, because Python reads `None` as falsy in `STILL_FAILING if recent_failed else RECOVERED` — exactly the inference the module's own docstring says a currency answer must not make (an absence of evidence is not the same as a recovery). `schema.sql`'s `escape_verdicts` table declares `recent_runs`, `recent_failed` and `recent_checked_at` as three independently nullable columns with no `CHECK` tying them together, so "all three are null together, or none are" is a convention the write path (`_store_currency`) happens to honour rather than something the schema enforces. No row violates it today, as far as a local check could tell, but nothing stops one.
- **`escapes.py`'s candidate query interpolates the landed-status literal directly into SQL** (`landing.status = '{webkit_checkout.LANDED}'`, in the `CANDIDATE_SQL` string) **while the otherwise-equivalent `unaskable` query binds the same value as a parameter.** The value is not request-derived, so this is not a live injection risk, but it is the one interpolated literal in an otherwise fully-parameterized module and should be bound the same way for consistency.
- **`TREE_DIVERGED`'s "newest build of the pull request" lookup and the escape-counting queries already bound the newer build to `started_at <= landing.landed_at`** (`CANDIDATE_SQL` and the `convictions()` query in `escapes.py`) — this is fixed; an earlier version of this check had no upper bound and mis-attributed post-landing builds as divergence.

## Filters, sorting and the tests/escapes tables

The filter-and-sort rework has a strict build order: the column registry and canonical URL grammar had to exist (done) before any page could stop using the grammar it replaces, and each remaining stage below depends on the registry being in place, which it is (`ews_dashboard/analysis/filters.py`). What remains:

- The `find=`/`sort=`/`dir=` query parameters are gone; every page speaks the `f.<table>=column:op:value` / `s.<table>=column:direction` grammar now.
- **The escapes listing is filtered, sorted and paged through the registry, and the 200-row cap is no longer a silent truncation.** `filters.ESCAPES` registers the listing's columns beside `TESTS`; `escapes.convictions` takes `conditions`, `sort_keys`, `limit` and `page` and returns a `ConvictionPage` carrying the total, so the head says "1–200 of 349, 149 more after this page" and a pager reaches the rest. The default order is escape strength descending, computed through `strength_for_counts` registered on the connection as a sqlite function (`db.register_functions`) rather than stored or re-spelled in SQL, so the figure the table orders by is the one it prints. Not an open item; recorded because the next two bullets are what it left behind.
- **The escapes page's verdict category is still its own `verdict=` argument rather than a clause in the table's grammar, so the registry's `verdict` column can only narrow within the open bucket or to nothing.** The route applies `outcome.verdict IN (...)` for the open category and a reader's own clauses on top of it, which means `f.escapes=verdict:eq:CONTAINED` while the pane has ESCAPED open matches no row — correct, and useless. The one pairing that does intersect is a clause naming either half of the merged ESCAPED bucket, which is how a reader asks for that half on its own. Folding the pane's links into `f.escapes=verdict:...` would unify them and make the category multi-select for free; it also rewrites every category link and the tests that read them, which is why it was not done here.
- **Escape strength is printed, sorted and offered only on the categories that have it.** The strength cell prints a figure for the two verdicts in the merged ESCAPED bucket and renders `—` everywhere else, and the column used to sort on all of them: a descending arrow over a full column of dashes, ordering rows by a figure that was nowhere on the page. Taken as the second of the two options this item offered — the heading is dropped from those categories rather than the figure being given a non-escape name — so a category outside the bucket now reads by landing time, which it prints, and offers no strength sort at all. `NO_BASELINE` rows do carry a real computed bound, so if that bound is ever wanted there the remaining option is to print it under an honest name. Not an open item; recorded because it closes the older pair of strength-dash tickets and names what was chosen.
- **`/tests` still caps at 1000 rows with no paging, where `/escapes` now pages.** `convictions.convicted_tests` reports `total`/`truncated` and the header says how many of how many, so nothing is silently cut — but the remainder is unreachable there. The `page` argument is deliberately read on `/escapes` alone, and `tests/web_test.py` asserts `/tests?page=2` still ignores it.
- **The escapes page shares `DEFAULT_WINDOW_DAYS = 7` with every other page (`app.py:24`), and on this page alone that default can be structurally empty.** An escape verdict cannot settle until `ESCAPE_WINDOW_DAYS` (3) after the landing plus `RUNS_SETTLING_SECONDS` (2 days), so a build whose pull request landed within roughly the last 5 days cannot hold a settled verdict, and the window filters on `build.started_at` (`escapes.py:114`). A 7-day window therefore only ever catches a two-day sliver, and only for pull requests that landed almost immediately after their build. Measured on 2026-09-21 the 7- and 14-day windows held 0 verdicts while 30 days held 7,911 — most of that was a stale checkout, but the settling floor remains and a reader landing on a blank page reads "no escapes" where the truth is "nothing in this window is askable yet". Either give this page its own wider default or say on it that the recent window is not yet answerable.
- **The `/tests` and `/explore` pages' surfaced-tests list is still driven by a `test=` query parameter read in the templates** (`tests.html`, `explore.html`) rather than built server-side the way the rest of the filter grammar now is.
- **The escapes table scrolls horizontally with its first column pinned, and the two warts that left are below.** The convictions table carries a measured `min-width: 150ch` and `#convictions > .body` is the scroller, because that table cannot take a `.table-scroll` wrapper without a template change; the test name is `position: sticky`. Before this the table had no width floor, so a narrow viewport shrank it instead of scrolling it: at 1000px the `Test` and `Why` headers broke inside their own single words into one-letter vertical stacks, rows ran past twenty lines, and `Current damage` was cut off at the pane's right edge. Not an open item; recorded because the next two are what it left behind.
- **The convictions table scrolls at 1500px, where it used to fit.** `min-width: 150ch` is about 1285px and the detail pane has roughly 1162px at that viewport. Deliberate: the floor buys four-line rows at every width below 1800 instead of six to eight at 1500 and twenty-two at 1200. Dropping to about 135ch would fit 1500 again by a handful of pixels, which is too fine a margin to rely on and re-crowds the `Why` column. Revisit only if the column set changes.
- **The filter form's label column is a fixed width sized by eye to hold the sort toggle.** `dashboard.css` sets `--chip-label-column: 3.5rem` on `.table-filter .chip-form` so the disclosure's own toggle, which sits above the grid and cannot join it, still falls inside the column the `Filter` and `Sort` labels share. The toggle grows with the number of active clauses and passes that column at around ten of them, where it will sit a few pixels wide of the labels' right edge. A grid whose first track sizes to `max-content` cannot see the toggle, since a `details` lays its content out inside `::details-content`, so the honest fixes are to move the toggle into the form or to derive the column width from the toggle's own text.
- **A horizontally scrolling table has no scrollbar affordance until it is scrolled**, on macOS Chrome, so a reader at 1200px cannot see that columns exist to the right. `.table-scroll` on `/tests` has always had the same property, so this is one shared fix in `dashboard.css` and not an escapes-page item — an always-visible gutter, or a shadow on the scrolled edge.
- **`/tests` and `/escapes` have diverged on paging.** `/escapes` now pages with a stated remainder, while `/tests` still truncates at a fixed cap with no paging and a test asserts that `?page=2` is ignored there. The grammar is shared, so the two tables should behave the same way; giving `/tests` the same paging is the remaining half of this stage.
- **`ews_dashboard/web/static/dashboard.js` has grown to 432 lines** doing real progressive-enhancement work (widening chip controls without a page reload), which makes nine comments stale — `ews_dashboard/web/templates/tests.html:16` and `:80`, `ews_dashboard/web/templates/parts.html:110`, `ews_dashboard/web/templates/explore.html:83`, `ews_dashboard/web/chart.py:3` ("There is no JavaScript on any page of this dashboard", the flattest of them), `ews_dashboard/web/static/dashboard.css:747`, `:1251`, `:1356`, and `ews_dashboard/web/app.py:28-29` ("The freshness banner is dismissed by a request rather than in the browser, because this page needs no JavaScript and a dismissal has to hold on the next page too."). The rule was never "no JavaScript" — it is that every control stays answerable by a plain server-rendered submit with the script disabled. The `queue_dropdown` macro comment at `ews_dashboard/web/templates/parts.html:20-30` already states it correctly and is the model the other nine should copy.
- **The chart's hover target is still a 3px circle with no enlarged hit area**, and its container still carries `role="img"`, which makes its children presentational to assistive tech even though a `<title>` is present on the point. A transparent, larger hit circle plus dropping `role="img"` would fix both; this has not been checked in an actual browser.
- **The caveat sentence on the escapes page — "Undecided convictions are counted above, not dropped" — is unchanged.** On one local measurement over a 14-day window, a meaningful share of convictions were landed and resolvable with no stored verdict at all, and those appear in no tile on the page; the sentence is still accurate as far as it goes, but a fourth metric naming that group explicitly has not been added.

## Queue selection

The queue picker was rebuilt from a flat set of platform chips into a three-level collapsible tree (group, OS version, queue), because the flat chips undercounted: prefix matching like `LIKE 'macOS%'` missed suites such as `API-Tests-*`, and two platforms had no chip at all, leaving a large fraction of builds unreachable by any chip on a local measurement. The tree is in place (`ews_dashboard/web/templates/parts.html`, the `queue_dropdown` macro), with `aria-label`s on the otherwise-unlabelled group/version checkboxes and a comment on the macro that accurately describes its no-JS/with-JS split. Left to verify or finish, in no particular order since none blocks the others: ticking a parent should submit only the parent's own scope parameter rather than every builder it currently contains, so a queue added later stays covered; the `indeterminate` state on a partially-selected parent needs to be computed from server-rendered selection on page load, not only by script after a user click; and the checkbox should align to the top of an open group rather than drifting to its vertical middle. These were design decisions made before the rebuild and have not been individually re-confirmed against the current template.

## Ingest and refresh

- **The API-tests flakiness property gap is fixed and its yield understood: only builds after the property's own deployment carry it, so a re-ingest cannot retroactively supply history that was never recorded.** This is not an open item; recorded here because it explains why API-tests coverage looks sparse for any window that includes the deployment date.
- **`results-db_jsc_pre_existing` is still never read.** `ingest.py` only reads the first-run and second-run pre-existing properties; JSC builders are excluded from that path entirely by the negative-lookahead pattern in `suites.py:61` (`(?!JSC-)`), which exists because JSC's suite names cannot be told apart from the others by a simple prefix. Reading the JSC property needs its own path the way the API-tests fix above needed its own read, not a tweak to the shared pattern.
- `refresh.py`'s crash handling and its default window already match the widest window a page can request, and a fatal error record already retains the partial ingest count reached before the failure.
- `results_db.py`'s `WithinStepCleanTree` classification convicts on a single row with no pull-request or author threshold, and does not compare the evidence's PR numbers against the build's own, so a pull request's own earlier build can be read as proof its own failure predates it. This lives in WebKit's EWS classification code, not in this repository, so the fix is a change there; local evidence for filing it is GTK-WK2-Tests-EWS build 153043.
- `config.py`'s `RULE_DESCRIPTIONS` text for `DirtyTree` states an author-count threshold that should track the one EWS's own classification code actually enforces; this repository has not independently re-checked that the two numbers still agree, since the source of truth is external to it.

## Miscellaneous

A UX review pass over the app found several smaller issues not yet addressed: a freshness-staleness banner that is dismissed by default rather than shown only when stale; provisional verdicts counted inside sets presented as decided; page navigation that drops the current suite/builder selection when following certain links; a trend-chart day-bucketing note whose referenced constant no longer exists under that name in the code, worth re-deriving before trusting it; and a couple of small chart/label inconsistencies (an "all states" badge duplicating a separate "clear" control, gridline labels off by one step). The escapes drilldown's missing remainder indicator was on this list and is fixed — the listing pages, and its head names the range, the total and how many are left. None of the rest has been re-verified individually against the current templates; treat this paragraph as a punch list to re-derive from the running app rather than as confirmed findings.

## Developer setup

- **`scripts/setup.sh` covers a fresh database only; it has no live-database path, by design.** It installs dependencies, creates the database, runs the tests and does a first ingest, refusing to run if the target database already exists unless `--force`, and it only ever prints (never runs) the escape-detection command. Migrating an existing database still follows the backup-then-migrate recipe in the handoff by hand — the migration scripts under `scripts/migrate_*.py` are not wired into `setup.sh`, and should stay that way, because auto-migrating a live database from a setup script is exactly the mistake the fresh-only guard exists to prevent.
- **A builder whose Buildbot walk fails is not retried, and nothing on any page says a queue is short.** One 90-day ingest on 2026-09-21 lost 11 of 41 builders — 6 to `HTTPError: HTTP Error 502: Bad Gateway` and 4 to `IncompleteRead`, both transient upstream conditions rather than defects here — so those queues carry a gap for that window while every rate computed over them reads as though the walk were complete. `ingest_builder` records the failure in the report and the run's `builds_failed`, but a reader cannot tell which queues are affected. Re-running with `--builder NAME` fixes one, so the missing pieces are a retry around the transient cases and some way for a page to say a queue is incomplete.
- **The escape pass has no defence against the machine sleeping, and the documented invocation does not mention it.** The handoff and the README both say to run it detached with a log file, which is necessary but not sufficient: one pass on 2026-09-21 took 16 hours of wall clock to do roughly 3 hours of work because the host slept overnight, and a reader watching the log sees no output during the assess phase either way, so a suspended run is indistinguishable from a slow one. Prefixing the documented command with `caffeinate -i -m` (or attaching `caffeinate -i -m -w PID` to a run already in flight) is the fix on macOS.
- **`assess()` reported an `unavailable` outcome that no verdict name covers.** The 2026-09-21 pass ended `{'FAILS_ON_MAIN': 2282, 'CONTAINED': 1834, 'ESCAPED': 349, 'TREE_DIVERGED': 3446, 'unavailable': 142}`, and `unavailable` is not one of the six verdicts in `escape_verdicts`' `CHECK` list, so those 142 convictions are counted in the run's summary but stored nowhere and are invisible on the page. Whether that is a results.webkit.org failure being swallowed or an expected absence has not been established; it wants tracing before any number resting on the decided total is quoted.
